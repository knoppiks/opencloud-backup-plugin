# Project Review — September 2026 (after Phase 6)

Scope: every planning document, every non-test source file under `pkg/`,
`cmd/`, `deploy/`, the CI workflow, and the pinned kopia v0.23.1 source where a
finding depends on library behaviour. Line references are as of commit
`70d668b` ("Add Phase 6 scheduling, durable state, and notifications").

Remediation options live in [`remediation-plans.md`](remediation-plans.md).
This file records *what was found* and *why it matters*; it does not decide
what to do.

---

## Verdict

**The plan is sound. The implementation has a handful of silent-failure bugs
in the security core and one locked decision that is unsafe as implemented.**

What is right, and should not be reopened:

- Spikes before commitment; every high-risk assumption (CS3 read path, kopia
  as a library, Garage limits, extension packaging, admin-role detection) was
  validated against real software before a line of product code.
- kopia as the data engine; no hand-rolled crypto or dedup.
- Versioned key envelope with the whole header as AAD; Argon2id bounds checked
  before derivation; Recovery Key encoding designed for humans.
- Path A (admin Take-Out + offline `decrypt`) as the acceptance-critical path,
  structurally unable to decrypt, tested with OpenCloud stopped.
- Admin as a configuration actor only; Path B member-only and never-overwrite.
- Time-based retention, newest-snapshot protection, partial read = failed run.
- Testability discipline: interfaces at every boundary, injected clock,
  contract tests, a `noleak` test on the key package.

What is wrong is listed below, most severe first. Nothing requires a restart.
The recurring theme is not bad design but **documentation running ahead of
code**: `decisions.md` and `README.md` describe several properties the
implementation does not yet have, and a reader who trusts the prose would
believe the system is safer than it is.

## F1 — Key envelopes are not durable (decision #16 as implemented)

**Severity: critical. Data-loss path for the only server-side copy of a
Space's SRW-wrapped Data Key.**

- RK and SRW envelopes for a Space live in **one document** `keys/<space-id>`
  (`pkg/keys/keys.go:79-85`). Every mutation is read-modify-write of the whole
  document (`pkg/keys/state.go:120-145`).
- A replace in the CS3 state store is **delete-then-upload**
  (`pkg/cs3state/cs3state.go:147-158`). A crash between the two leaves no
  document: **both envelopes gone**.
- The window is hit on every first setup: `PutRK` creates the document,
  `PutSRW` replaces it (`pkg/api/keys.go:130-139`).
- **The SRW envelope exists nowhere else.** Only the RK envelope is published
  to S3; `PublishTo` refuses any other kind (`pkg/takeout/publish.go:69-74`).
- The state Space is not backed up, not versioned, and nothing validates that
  no end user is a member of it (`cs3state.go:259-285` matches on id only).
- The comment "every record this store holds is either re-derivable or
  re-uploaded on the next write" (`cs3state.go:149-150`) is **false** for
  `keys/`, `targets/` (TW-wrapped S3 credentials) and `spacecfg/`.
- Reva's real behaviour on `InitiateFileUpload` for an existing path
  (`ALREADY_EXISTS` vs. silent overwrite creating a revision) was never
  verified. The unit test asserts one behaviour against a fake
  (`cs3state_test.go:205-222`); the integration test cannot tell which branch
  ran (`cs3state_integration_test.go:114-125`). Either way, every lease
  renewal (~every 3 m 20 s per running Space) and every job finish produces a
  trashed document or a revision that is never purged.
- State availability equals OpenCloud availability. The scheduler's memory,
  including key custody, dies with the system it protects. After a rebuild
  (new Space ids, decision #4) nothing can resume unattended backups; Path A
  is the only remaining path — which is by design, but the plan does not say
  so explicitly.

**Assessment of decision #16:** defensible for jobs, leases, run history and
notification events (low value, re-derivable, or append-only by construction).
**Not defensible for key envelopes, target credentials and Space
configuration** without an atomicity mechanism. The decision does not need to
be reversed, but it needs a carve-out.

## F2 — Key ceremony has no guards

**Severity: critical. Any member can permanently brick a Space's backups.**

- `handleKeySetup` (`pkg/api/keys.go:77-147`) never checks `Status` first.
  A second `POST .../backup/setup` with a fresh client-generated DK overwrites
  both envelopes. The kopia repository on S3 was initialised with the old DK
  (`initializeIfNeeded` treats `ErrAlreadyInitialized` as success,
  `pkg/snapshot/engine.go:461-469`), so `repo.Connect` now fails with the new
  password: every backup and every Path B restore fails from then on. There is
  no API to recover. The next successful run would also overwrite the S3
  `recovery.ocbke` with the new envelope, which does not match the old
  snapshots.
- The server cannot verify that the RK envelope wraps the DK it received
  (`keys.Inspect` at `keys.go:118` parses the header only). A client bug means
  Path A fails only at recovery time. This is unfixable server-side and must
  become a documented client invariant for Phase 8 (self-unwrap before POST).
- `RotateSRW` / `RotateRK` (`pkg/keys/service.go:111-125`) have **no callers**
  outside tests. Rotating `SRW_KEY` today makes every stored SRW envelope
  unopenable (`runner.go:441-446` → `ErrNotConfigured`).
- No server-side floor on client Argon2id parameters: `time=1, memory=1 KiB,
  lanes=1` is accepted (`pkg/keys/envelope.go:265`).
- `PutRK` then `PutSRW` are two writes; a failure between them yields
  `HasRK=true, HasSRW=false` and the only recovery is re-running setup, which
  regenerates a Recovery Key the user has already written down.

## F3 — Membership check ignores role, expiry and groups

**Severity: high. A viewer-only or expired share grants full backup control.**

`isMember` (`pkg/api/api.go:235-246`) is `Owner == subject || subject ∈
Members`. `Members` is built from the `grants` opaque key only
(`pkg/cs3/client.go:365-386`); the role value is parsed into `roleLabel` and
then **never used**. `grants_expirations` is never read (no hits in `pkg/`).
`groups` is never read, so group-shared Spaces deny every member (fail-closed,
but broken). Consequences: a read-only member can reset keys (F2), trigger
runs, list snapshots, and restore gigabytes into a Space they cannot otherwise
write to — the restore runs under the service account.

The `grants` map shape is described as "varies by reva version"
(`client.go:362`) and nothing pins it against the fixture.

## F4 — Two kopia defaults silently produce empty or partial "successful" backups

**Severity: high. Both undermine the ransomware threat model directly.**

1. **Ignore rules are active inside user data.** `Uploader.DisableIgnoreRules`
   is never set (`pkg/snapshot/engine.go:116-117`); kopia v0.23.1 then honours
   `.kopiaignore` files and `CACHEDIR.TAG` markers (`upload.go:1388-1393`,
   `policy_tree.go:29-31`). A `.kopiaignore` containing `*` synced into a Space
   — by a user, by malware, by accident — yields an **empty snapshot reported
   as success**.
2. **Checkpoint manifests are treated as snapshots.** kopia checkpoints every
   45 minutes (`upload.go:39-40`), saving a manifest with
   `IncompleteReason="checkpoint"` and flushing (`upload.go:538-549`). The
   engine never calls `policy.ApplyRetentionPolicy` after a successful upload
   (the kopia CLI does; it is what deletes old checkpoints) and never filters
   `IncompleteReason` in `List`, `findManifest`, `expiredManifests`, `toInfo`
   (`engine.go:158-177, 339-355, 527-561`) or in `decrypt -list`. Effects:
   - A failed run longer than 45 minutes **does** persist an incomplete
     snapshot, contradicting `decisions.md` "A partially-read Space is a failed
     run".
   - The restore picker and `decrypt`'s default (`infos[0]`,
     `pkg/takeout/decrypt.go:216-219`) may select a partial tree.
   - `expiredManifests` protects `sorted[0]`, which may be a checkpoint; the
     last *complete* snapshot can then be deleted.

   `assertComplete` (`engine.go:148-156`) protects only the final manifest of
   the run, not the checkpoints kopia already saved.

Neither behaviour is covered by a test (no run exceeds 45 minutes; no fixture
contains a `.kopiaignore`).

## F5 — S3 credentials are written to disk on every run

**Severity: medium. Contradicts decision #14 as written.**

`repo.Connect` (`engine.go:433`) serialises the storage `ConnectionInfo`,
including `SecretAccessKey`, into `repository.config` via plain
`json.MarshalIndent` (kopia `repo/connect.go:52-60`,
`repo/blob/s3/s3_options.go:24`; the `kopia:"sensitive"` tag affects display
only). The file is removed on normal exit (`engine.go:430`) and left behind on
crash or SIGKILL. `BACKUP_WORK_DIR` is a plain `emptyDir` in the manifest.

## F6 — Deployment defeats the single-instance requirement

**Severity: high (operational). Every rollout violates a binding constraint.**

- `deploy/deployment-backupd.yaml:12` sets `replicas: 1` but no
  `strategy: {type: Recreate}`. Default `RollingUpdate` (maxSurge 1) runs two
  pods against one state Space during every image update. The new pod's
  `Recover` (`pkg/jobs/lease.go:224-252`) does not hold the old pod's lease
  locally; if renewal lags, it marks a live run failed and both schedulers may
  dispatch the same Space. `decisions.md` says this is "unsupported"; the
  manifest ships it.
- `STATE_SPACE_ID` unset (as shipped, `deployment-backupd.yaml:105-106`) falls
  back to memory with a warning (`cmd/backupd/main.go:405-411`). Users complete
  key setup, the pod restarts, envelopes and schedules vanish.
- `OC_SERVICE_ACCOUNT_ID/SECRET` are commented out in the manifest.
- `secret-wrap-keys.yaml:20-21` still refers to "the app's database".

## F8 — Scheduler and runner robustness

**Severity: medium. Each is a silent-stop failure, the class the plan says it
fears most.**

- **Lost `Finish` write wedges a Space forever.** `Runner.finish` logs and
  continues if `Jobs.Finish` fails (`runner.go:242-249`); `release` then
  deletes the lease (`lease.go:206-216`). The job stays `running` with no
  lease; `Recover` iterates leases only, so it never sees it; `due()` returns
  false while any job in the last 10 is non-terminal (`scheduler.go:276-281`).
  **The Space is never scheduled again.** `ListRunning` exists
  (`jobs/state.go:181`) and is unused. Same path via `Runner.fail`.
- **Scheduled runs have no timeout.** `StartBackup` bounds manual runs at 6 h
  (`runner.go:186`); `RunScheduled` → `run()` (`runner.go:160-172`) does not,
  and the scheduler sets no `RunTimeout` (`main.go:457-480`; the comment at
  `scheduler.go:105-107` claiming "the runner has its own" is wrong for this
  path).
- **No body-read deadline** on data-gateway GETs (`main.go:569-574` sets
  `ResponseHeaderTimeout` only). A stalled stream holds the Space lock until
  the (absent) timeout.
- `LeaseLocker.Acquire` holds the process mutex across two CS3 round-trips
  (`lease.go:129-150`), serialising all lock acquisitions on gateway latency.
- `Documents.All` swallows decode errors (`pkg/state/state.go:217-238`): a
  corrupt `spacecfg/<space>` vanishes from `List`, so the Space is neither
  scheduled nor flagged stale — the monitor reads configs through the same
  path.
- Notification events are never pruned (`notify.StateStore.PruneBefore` has
  no caller).
- Idle cost: per tick, `Recover` + `Configs.List` + `ListRecent(10)` per Space
  + `Monitor.Sweep` doing `ListRecent(20)` again, each CS3 call preceded by a
  fresh `Authenticate` RPC (`pkg/cs3/client.go:66-89`). Order of hundreds of
  gateway calls per minute for ten Spaces while nothing is happening.

## F9 — OIDC validation gaps

**Severity: low-medium in a single-IdP family deployment; one-line fixes.**

- `OIDC_AUDIENCE` is optional and defaults to empty (`oidc.go:158-160`,
  `main.go:150`): any token from the same Konnect issuer, including ID tokens
  or tokens for other clients, is accepted.
- `exp` is only checked if present (go-jose skips validation when
  `Expiry == nil`); a token without `exp` is valid forever. Untested.
- JWKS is refetched on every unknown `kid` (`oidc.go:305-314`) with no
  negative cache — an unauthenticated refresh amplifier.
- Startup hard-fails if the IdP is down (`main.go:144-147`); crash-loop rather
  than degrade.

## F10 — Smaller findings

- `retention_days` has no floor; `1` is accepted (`pkg/api/backup.go:130-133`).
  A user session (or malware holding it) can collapse retention.
- `Path B` "never overwrite" rests on the timestamped folder name alone
  (`restore.go:486-489`, second granularity); `MakeDir` swallows
  `ALREADY_EXISTS` (`writer.go:121`) and reva does not return `ALREADY_EXISTS`
  on upload, so a backwards clock step could overwrite.
- Path B against real reva is unverified: `simple` PUT semantics,
  `X-OC-Mtime` honoured or not, zero-byte files, empty directories.
- `SRW_KEY == TW_KEY` is not rejected; one copy-paste collapses the
  "rotate independently" rationale.
- Bootstrap S3 credentials stay in the pod environment forever after being
  sealed once (`main.go:523`, `bootstrap.go:70`).
- Envelope publish failure is non-fatal and logged only (`runner.go:402-427`);
  Path A then degrades silently until the next successful run.
- `readyz` performs an unauthenticated `Authenticate` + `ListStorageSpaces` per
  probe (`main.go:577-587`).
- The `takeout` binary links `pkg/takeout`, which contains `Decrypt`; the
  "no key input" audit greps `cmd/takeout/main.go` only
  (`cmd/takeout/main_test.go:26-64`). The guarantee is "no reachable path",
  which is fine, but the test is narrower than the claim.
- kopia mtime+size cache hit with no content hash: a file replaced with equal
  size and preserved mtime is skipped. Inherent to kopia; worth stating.
- Scheduler default timezone is UTC unless `SCHEDULE_TIMEZONE` is set
  (`main.go:470`) while the default schedule comment says "service timezone"
  (`spacecfg.go:27`). A family will read `02:30` as local.
- The threat model discusses SRW/TW/S3 credential leaks at length and barely
  mentions `OC_SERVICE_ACCOUNT_SECRET`, which grants owner scope on every
  Space in plaintext and is the actual crown jewel.

## F11 — Weight that buys nothing (not bugs)

- `pkg/s3target` is dead code; a fourth copy of the S3 tuple
  (`targets.Target`, `snapshot.Location`, `objstore.S3Config`).
- Every store ships a `MemoryStore` and a `StateStore` with duplicated logic,
  plus a contract suite to keep them aligned; production wires only
  `StateStore`, and `state.NewMemoryStore()` already provides an in-memory
  backend.
- Three grant scopes (`ScopeAllUsers/User/Space`) with no admin API to create
  any; bootstrap creates only `ScopeAllUsers`.
- Three overlapping lock layers (`due()` history scan, `inflight` map,
  `LeaseLocker` mutex + lease) for one guarantee.
- `Client.Walk` and `SpaceReader.Walk` are dead in production.
- `.golangci.yml:26-30` disables `unused` for all of `pkg/`, which is why the
  above went unnoticed.
- `pkg/keys.Store` methods take no `context` and manufacture 30 s contexts
  internally (`keys/state.go:105, 125`), unlike every other store.

## Test-coverage gaps (things no test exercises)

- Runs longer than kopia's 45-minute checkpoint interval; incomplete manifests
  in `List`, `Prune`, `decrypt -list`.
- `.kopiaignore` / `CACHEDIR.TAG` inside a Space.
- Re-running key setup on a configured Space.
- Expired grants, group grants, role-restricted members.
- Reva overwrite semantics for `InitiateFileUpload` on an existing path;
  trash/revision accumulation in the state Space.
- Any CS3-state or OpenCloud-dependent test in CI.
- Path B against real reva.
- Files > 2 GiB (kopia parallel parts + `Range` on the data gateway).
- Data-gateway stalls, transient errors, body-read timeouts.
- Maintenance actually reclaiming bytes (two GC cycles with `SafetyFull`).
- Crash mid-run: leftover `repository.config`, orphan packs.
- Two instances against one state Space (the rollout case).
- Token without `exp`; token with wrong/absent `aud`.
- Windows-invalid filenames and case collisions in `decrypt` output.

## Plan-level gaps (missing from the roadmap, not bugs)

1. **Post-rebuild Path B.** Decision #4 acknowledges that a rebuilt OpenCloud
   has new ids. The repo prefix `spaces/<old-id>/` is then orphaned and the
   state is gone, so only Path A remains. A "re-attach an existing repository
   to a new Space using the Recovery Key in the browser" flow is the natural
   disaster-recovery story for a family and is not planned.
2. **Operational key rotation** (SRW, TW, RK) has no owning phase.
3. **Real-OpenCloud CI.** Nothing pins reva semantics the system depends on
   (upload-overwrite, `X-OC-Mtime`, `grants` shape, service-account scope).
4. **Maintenance/GC** is Phase 7, but zero maintenance is already a
   correctness and cost problem after Phase 4 (orphans, index growth).
5. **Explicit deployment preconditions**: TLS at ingress, single instance,
   state Space provisioning runbook, memory-backed work dir.
